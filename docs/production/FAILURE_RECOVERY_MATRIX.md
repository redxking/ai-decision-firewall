## Safety rule

After a possible effect, the system and operator report the most conservative supportable state. A broker acknowledgement, `SyntheticAdapterReceipt`, or state digest is not independent proof of effect; missing receipt is not proof of no effect; failed readback is not proof of no effect; a described rollback is not an executed rollback; and incomplete audit is not audit closure.

T1 control reservation, T2 adapter state-plus-receipt, JSONL audit, separate read-only observation, and T3 terminal control result are distinct boundaries. There is no cross-store transaction. Reconciliation is an explicit operator action under exclusive, quiesced ownership via `reconcile_request(operator_asserted_quiesced=True)`; it is never automatic in a constructor and never issues a command.

Supported processes serialize first-open and every durable firewall operation through a bounded POSIX directory-root `flock`; the complete JSONL lifecycle is additionally serialized by an exclusive audit-file `flock`. Public store constructors use the bounded first-open fence even outside the combined firewall. These controls are cooperative and same-host only. They are not a distributed lease, fencing epoch, hostile-writer defense, failover, HA, or DR.

Existing stores are preflighted before any missing artifact is created. Each store validates its exact schema fingerprint, metadata, canonical row digests, semantic relations, and timestamp chronology. Adapter validation also requires each target's receipt state/time chain to end at its current state. Startup and durable use correlate authority-free control and adapter projections and fail closed on defined orphan, omission, provenance-substitution, receipt/disposition, and terminal-target mismatches. Detection does not create cross-store atomicity or independent custody.

### Durable objects and conservative interpretation

| Object / state | Permitted interpretation |
|---|---|
| `ISSUED` authorization | Registered but not consumed. Under explicit quiesced recovery it may become `REVOKED`; it is never silently reused after an incident. |
| `CONSUMED` authorization | Consumed atomically with attempt reservation; it never reopens. |
| `REVOKED` authorization | Permanently nonexecuting; it never becomes `ISSUED`. |
| `RESERVED` attempt | Command execution may be active or may have crossed T2. It is never an operator-approved retry state. |
| `RECEIPT_RECORDED` attempt | An exact adapter receipt reference is present, but verification-scoped terminal closure is not yet recorded. It is not success and never permits command replay. |
| `SyntheticAdapterReceipt` disposition `NO_EFFECT` | Adapter-reported affirmative no-effect for the exact canonical binding. If valid and exact, recovery may close `FAILED_NO_EFFECT`; it is not a claim about an external target. |
| `SyntheticAdapterReceipt` disposition `APPLIED`, `PARTIAL`, or `AMBIGUOUS` | Adapter-reported only. Without separately durable verification, recovery closes `UNKNOWN_EFFECT`, not success. |
| no receipt | Absence does not establish no effect. Recovery closes `UNKNOWN_EFFECT`; automatic retry remains prohibited. |
| corrupt, mismatched, or unavailable adapter evidence | Reconciliation halts with no control-state transition. Processing remains disabled. |
| `VERIFIED_EFFECT` | Separate repository-controlled observation supported the expected synthetic state before T3 closure. It remains same-project/same-store evidence and is not an operational-effect claim. |
| `FAILED_NO_EFFECT` | Exact bounded synthetic evidence supports no effect for this attempt; no automatic retry. |
| `RECOVERY_REQUIRED` | A terminal synthetic disposition requires separately authorized handling; it does not prove compensation or rollback. |
| `UNKNOWN_EFFECT` | Effect may have occurred. Terminal quarantine: no retry, replacement token, fabricated verification, or rollback claim. |
| terminal `RequestLookupResult` | Closed, versioned, sanitized projection of the recorded terminal disposition. It is not `Phase3Result`, executable authority, or independent verification. |
| recovery JSONL prefix/trio | Only the exact contiguous sequence `RECOVERY_STARTED`, `RECOVERY_EVIDENCE_ASSESSED`, `RECOVERY_FINALIZED` is valid. A pending exact prefix or completed trio before T3 owns the audit tail; other request/approval audit writers fail with `RECOVERY_AUDIT_PENDING`. |

### Status vocabulary

- `BASELINE_TESTED`: covered by synthetic tests at or before the baseline.
- `STAGE_A_CANDIDATE`: implemented or documented in published exact Stage A Commit `8818d5d2`; project-controlled verification exists, but the named production property and owner acceptance remain incomplete.
- `PARTIAL`: some bounded behavior exists, but a material production property is absent.
- `OPEN`: required behavior or acceptance evidence is absent.
- `NOT_APPLICABLE_BY_PROHIBITION`: the dependency/path is absent because Stage A prohibits it; this is not validation for a later stage.
