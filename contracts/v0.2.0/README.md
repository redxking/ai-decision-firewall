## Files

- `replay-case.schema.json` defines runtime case metadata and nested evidence events.
- `replay-adjudication.schema.json` defines evaluator-only labels stored in a separate JSONL file.
- `replay-manifest.schema.json` defines dataset provenance, approval and de-identification attestations, file roles, record counts, adapters, and SHA-256 digests.
- `replay-qualification.schema.json` defines the closed metadata-only ledger record for one governed nonblank case-source occurrence.
- `replay-rejection.schema.json` restricts that ledger shape to the `QUARANTINED` subset.
- `qualification-expectations.schema.json` defines closed metadata-only totals and predeclared per-record outcomes for a synthetic qualification campaign.
- `evaluation-evidence.schema.json` defines the claim, exact system and harness, evaluation scope, validity checks, raw counts, evidence artifacts, review state, limitations, and prohibited inferences required before reporting a result.
- `gate-b-authorization.schema.json` defines the closed authorization, approval, binding, control, custody, sampling, stop-condition, adjudication, review, and claim-control record required before historical payload access.
- `gate-b-ce2-campaign.schema.json` defines the closed campaign profile, sanitized attempt result, and summary artifacts for the fixed `P2-CE-003` synthetic Gate B campaign.
- `reference-feature-assurance.schema.json` defines one closed metadata-only successful reference-projection record per accepted case. It permits only the case identifier, normalized-case digest, expected/observed projection digests, and `matched=true`.
- `feature-assurance-ce2-campaign.schema.json` defines the closed plan/profile/result/summary shapes for the fixed `P2-CE-004` synthetic campaign.
- `source-to-decision-assurance.schema.json` defines one closed metadata-only successful reference-path receipt per accepted case, binding the exact normalized case, model, policy, execution mode, five ordered semantic surfaces, and complete path by digest.
- `source-to-decision-ce2-campaign.schema.json` defines closed plan/profile/result/summary shapes for `P2-CE-005`. The schema permits representation of future evidence but does not create or validate an observed campaign result.
- `examples/phase2-starter-evidence-record.json` is a worked CE-2 controlled-behavior record for the three-case synthetic fixture. It is not historical or operational evidence.
- `examples/phase2-qualification-evidence-record.json` is the CE-2 controlled-behavior record for the fixed seven-record qualification campaign and exact `evidence/phase2_qualification/` bundle. It is not historical data-quality, efficacy, alignment, or live-shadow evidence.
- `examples/phase2-gate-b-ce2-evidence-record.json` is the CE-2 controlled-behavior record for two complete repetitions of the fixed 16-scenario synthetic Gate B registry and the exact `evidence/phase2_gate_b_ce2/` bundle. It is not a real approval, historical-data, efficacy, independent-assurance, alignment, or live-shadow result.
- `examples/phase2-feature-assurance-ce2-evidence-record.json` is the CE-2 controlled-behavior record for two complete repetitions of the fixed 16-attempt typed-feature/reference-projection registry and the exact `evidence/phase2_feature_assurance_ce2/` bundle. It is not historical/live, efficacy, independent-assurance, alignment, or production-readiness evidence.
- `examples/gate-b-authorization-draft.json` is a schema-valid, expired, placeholder-only `DRAFT`. It is not an approval, authorization record, signature, custody record, or historical-data binding, and a historical runtime must reject it.

For replay manifests, whole-dataset cases, and adjudications, the Python validator in `src/adf_poc/replay/contracts.py` is the executable POC authority. It enforces constraints that JSON Schema cannot express cleanly, including repository-path confinement, file digest and record-count verification, globally unique case and event identifiers, timezone-aware timestamp ordering with `collected_at >= observed_at`, runtime-label exclusion, exact type/range and source authority for modeled attributes, and equality between canonical `asset_id`, `privilege_level`, `break_glass`, and `asset_criticality` values and every corresponding asset-inventory assertion.

Modeled Booleans require exact JSON Boolean values and code-authorized sources. `failed_logins` is authorized only for `identity` and accepts only finite integral JSON numbers in `0..1,000,000`, including integral floating JSON representations such as `10.0`; strings, Booleans, fractions, non-finite values, negatives, and over-bound values fail closed. Every JSON numeric value anywhere in an accepted case must be finite before engine invocation. Unrecognized attributes remain bounded opaque context and cannot become features. `source_conflict` is separately governed as a network-only JSON Boolean because it can drive evidence-quality assessment without entering the 20-feature vector; under `QUARANTINE_RECORD`, wrong source maps to `SEMANTICS / UNAUTHORIZED_DECISION_SIGNAL` and wrong type maps to `SEMANTICS / INVALID_BOOLEAN`. Reference feature assurance does not recompute it.

For `QUARANTINE_RECORD`, `src/adf_poc/replay/qualification.py` owns bounded parsing and fatal/quarantine classification, and the harness independently verifies the resulting schema, source-line/hash binding, ordered rejection projection, `input = accepted + quarantined`, and `accepted = decisions` invariants. The policy is limited to the `cases` role in offline `HISTORICAL_REPLAY`; `SHADOW_READ_ONLY` rejects it. `FAIL_DATASET` remains the default.

The qualification, rejection, and synthetic-expectation schemas are closed and metadata-only. They allow source/run identity, physical and nonblank ordinals, SHA-256 values, status, stable error category/code, and campaign totals as applicable. They allow no source payload, parsed value, payload identifier, path, exception text, or free-form message. Hashes remain linkable and sensitive for historical data; they are traceability values, not anonymization.

Claim-evidence records are validated against `evaluation-evidence.schema.json` and cross-checked against their committed artifacts by `scripts/validate_claim_evidence.py`. The starter and qualification profiles check schema and format conformance, path confinement, artifact hashes and counts, run-manifest consistency, audit-chain integrity, per-case read-only audit records, empty authorization state, and the exact synthetic-only claim boundary. The `P2-CE-003` and `P2-CE-004` profiles bind their respective campaign plans, schemas, frozen source bytes, runtime/configuration profiles, result ledgers, raw denominators, summaries, review types, exact supported wording, and prohibited inferences. The `P2-CE-004` profile also freshly re-executes the corrected frozen evaluator. No `P2-CE-005` evidence profile or record is claimed at this stage; its plan remains CE-0 `NOT_EVALUATED`.

For a new alpha.6 replay, the harness first invokes the Phase 2.4 in-process reference projector after deterministic decision and eight-stage audit validation. It then runs the Phase 2.5 reference path from frozen normalized-case, decision, model, and policy bytes and compares `EVIDENCE`, `MODEL`, `POLICY`, `VERIFIER`, and `FINAL_SURFACE` in that order. Both persisted receipt files are metadata-only, duplicate-member-aware on readback, and hash/count-bound in the run manifest. A Phase 2.5 mismatch publishes neither receipt and stops before qualification/rejection publication, adjudication decoding, comparison, metrics, or completed-run finalization; earlier normalized, decision, and audit files may remain as incomplete diagnostic material.

The source-to-decision receipt binds deterministic semantic content, not volatile `decision_id`, `created_at`, `latency_ms`, or `decision_record_hash` instance values. The completed run manifest separately co-binds the exact raw decision and eight-stage audit bytes. A receipt alone is not a complete run or custody proof, and semantically equivalent runs may have identical receipts. The separate implementation remains same-process and same-project; agreement does not establish source truth, outcome correctness, policy fitness, external custody, or organizational independence.

Every run output is strict-parsed, structurally compared with its validated in-memory value, and exact-digest frozen immediately after write. The harness rechecks normalized cases, normalization diagnostics, deterministic decisions, both reference receipts, qualification/rejection artifacts when enabled, adjudication comparison, and replay metrics before manifest construction, after construction, and after manifest write. Volatile raw engine decisions and audit are exact-frozen and included in the same three-boundary checks and manifest digest map. The historical path applies the same checks through retained output-directory descriptors. `replay_run_manifest.json` is not self-hashed; successful harness return after final checks, not file presence, establishes completion.

## Gate B historical-data preflight

The Gate B contract separates manifest attestations from the external authority needed to process a historical, de-identified source. The closed top-level record contains `schema_version`, `authorization_id`, `status`, `dataset_id`, `dataset_manifest_sha256`, `approved_purpose`, `population_scope`, `window_start`, `window_end`, `valid_from`, `expires_at`, `approvals`, `artifact_bindings`, `controls`, `custody`, `sampling`, `stop_conditions`, `adjudication`, `independent_review`, and `claim_control`.

Historical preflight accepts only `status=APPROVED`. It requires exactly one approved record for each of `DATA_OWNER`, `MISSION_OWNER`, `SECURITY`, `PRIVACY_LEGAL`, and `RECORDS_MANAGEMENT`; an `APPROVED` review with an asserted reviewer identifier distinct from all asserted approver identifiers; and exactly one SHA-256-bound, confined relative artifact for each of `SOURCE_MAPPING`, `ADJUDICATION_PROTOCOL`, and `PILOT_PROTOCOL`. Runtime semantic checks also require `window_end <= custody.frozen_at <= valid_from`. An approved record must carry the fail-closed control values: direct identifiers removed and re-identification risk reviewed; offline only; no live feed, action credential, or write-capable connector; network egress disabled; runtime labels separated; complete-intake reporting; restricted-hash handling; frozen selection and thresholds; stop on fatal and unknown failures; separated adjudication with hidden labels and permitted indeterminate outcomes. These structural checks do not authenticate identity, independence, authority, or custody truth.

JSON Schema validates the closed structure and permitted values. Before payload access, runtime semantic validation additionally verifies current validity; ordered approval, review, freeze, predeclaration, source, authorization, and holdout times; `expires_at = claim_control.expires_at`; `sample_count = manifest cases record_count = historical_case_count`; `sample_count <= full_intake_count`; unique roles and declared category thresholds; exact dataset/manifest/model/policy/adapter/contract bindings; confined nonsymlink artifact paths; and artifact byte digests. Current validity is checked again before the runner, after the runner, and before final evidence completion. Only after authorized case qualification, but still before normalization or engine invocation, the runtime verifies an explicit threshold for every observed quarantine category, the observed overall and per-category rates, and accepted `opened_at` values against the approved half-open source window. Any zero digest, placeholder, missing or stale approval, mismatch, unexpected field, path escape, symlink, unknown condition, threshold breach, or failed control stops processing.

For `HISTORICAL_DEIDENTIFIED` origin, preflight ordering is mandatory. Until structural Gate B preflight passes, the runtime may read only configuration and manifest control bytes, the Gate B package, model and policy, and the bound mapping/protocol control artifacts. It must not open, hash, count, decode, parse, qualify, normalize, or adjudicate cases or adjudications first. In a restricted working copy, Gate B inputs must be stored under ignored `local/gate_b/`, and historical outputs must be written through retained directory descriptors into a new ignored, run-specific `outputs/replay/<run>/` directory with owner-only permissions. The historical runner receives no filesystem paths. See [`ADR 006`](../../docs/adr/006_gate_b_machine_readable_preflight.md) and the [`Gate B historical-pilot guide`](../../docs/phase2/GATE_B_HISTORICAL_PILOT.md).

Machine validation proves internal structure and byte binding only. It does not prove legal authority, approver identity, signature authenticity, effective de-identification, custody truth, or historical efficacy. The authorization snapshot and approval/reference fields may be sensitive and are excluded from public evidence summaries. A bounded opaque `authorization_id` may appear in a restricted aggregate trace summary only when it encodes no person, source, incident, system, or other sensitive fact. No actual historical data, labels, authorization snapshot, approval or custody evidence, source-specific mapping, endpoint, identity, or linkable historical digest may be committed to this public repository.

## Runtime/evaluator separation

Case input must not contain `compromised`, `expected_disposition`, `scenario`, adjudication, ground-truth, or equivalent label fields. Governed control documents and JSONL records reject duplicate object members rather than applying ambiguous last-member-wins parsing. The replay harness passes only normalized cases to the engine. For historical origin it freezes the separate adjudication bytes inside the harness before the engine, but does not expose their path or contents to the runner; decoding, semantic loading, and snapshot publication occur only after decisions and read-only audit checks close.

## Governance boundary

Only `HISTORICAL_REPLAY` and `SHADOW_READ_ONLY` are valid Phase 2 modes. `live_actions_enabled` is fixed to `false` outside this data contract. Both modes require explicit approved-use, de-identification, and no-direct-identifier attestations. The starter dataset is synthetic by construction and declares `historical_case_count: 0`; it is not historical evidence.

## Deterministic normalization

Evidence is sorted by normalized UTC `observed_at`, `collected_at`, `source_type`, `source_instance`, and `event_id`. Reordered cases are reported in `normalization_diagnostics.json`. Volatile engine artifacts retain timestamps, UUIDs, latency, and audit hashes, while the replay harness emits a separate deterministic decision projection, comparison file, metrics file, and artifact manifest. The run manifest records current-run digests and counts for raw decisions and audit records as well as digests for deterministic outputs; volatile hashes are not expected to match across runs.

The executable validator also applies bounded-input controls: at most 100,000 records per declared JSONL file, one MiB per JSONL line, 128 JSON object/array nesting levels during qualification, 10,000 events per case, 16,384 characters of untrusted text per event, 256 KiB of structured attributes per event, and 512 MiB per declared file. Gate B control JSON is bounded to one MiB and 128 nesting levels, each mapping/protocol artifact to two MiB, and the bound model and policy to 64 MiB each. The harness refuses to use a non-empty output directory so prior replay evidence is never silently overwritten.

The encoded line-size bound includes a terminal LF or CRLF. `raw_line_sha256` excludes only that delimiter and retains every other byte. The seven-record synthetic qualification fixture predeclares three accepted records and four quarantines—`INVALID_JSON`, `MISSING_REQUIRED_FIELD`, `INVALID_TIMESTAMP`, and `CANONICAL_CONTEXT_MISMATCH`. The result is a controlled accounting check with `historical_case_count=0`, not historical data-quality, efficacy, alignment, or live-shadow evidence.
